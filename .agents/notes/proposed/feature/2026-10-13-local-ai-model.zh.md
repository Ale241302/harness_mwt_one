# Agent Note: 桌面应用的本地模型，分阶段

Status: proposed

[English](2026-10-13-local-ai-model.md) | 中文

## Problem

桌面应用可以承载一个小型本地模型，但草率地发布「本地 AI」只会做出更差的产品：安装变慢、承诺它没有的知识、也无法判断模型是否就绪。产品负责人要的是一个仅属于桌面端的本地模型：(a) 安装程序只在硬件真的能跑时才预置它；(b) 用用户自己的工作成果来训练——Context、Memory、Routines、Workflows、Workspaces/Spaces、Agents、Skills——**但绝不用私有的**；(c) 在一个明确的开关控制下自主演化；(d) 一旦答不上来，就把问题交给用户的第三方服务商。

## Decision

决定已经做出，并附理由：

**运行时：Ollama，而不是 LM Studio。** Ollama 是无头守护进程，提供 OpenAI 兼容的 API，安装与模型管理都可脚本化，用户无需操作任何 GUI——正是后台预置所需要的。LM Studio 以 GUI 为先，没有无人值守的路径。Ollama 服务器本身就是一份 OpenAI 兼容的模型清单，因此可以作为 `provider: ollama` 直接进入 `packages/faberloom/model-catalog` 的提供商发现（`/v1/models`），无需新增协议。

**模型。** 一个小型、支持工具调用、具备推理能力的模型。默认：**Phi-4-mini-Instruct（3.8B，Q4_K_M ≈ 2.3 GB）**——按单位权重计，它在中等笔记本上推理与工具调用最强。最弱的合格机器上的更轻回退：**Qwen2.5-3B-Instruct（Q4_K_M ≈ 2 GB）**。图像输入是**可选升级**，不是基础承诺：`Qwen2.5-VL-3B` 只给放得下它的硬件，且产品要如实说明基础模型是文本 + 工具。没有任何一个 4B 以下的模型能把工具调用、推理和视觉同时做好，假装可以正是本决定要避开的陷阱。

**最低硬件——有意下调，因为训练器装得进一张 4 GB 卡。** 默认模型是 3.8B 的 LoRA，而 Soup 自己公布的记录就是在 4 GB 笔记本 GPU 上训练一个 8B，所以 3.8B 的 LoRA 远在其内。**有 GPU**：≥ 4 GB 显存——迷你 PC 和旧笔记本都算——走完整路径（推理 + LoRA 演化）。**没有 GPU**：≥ 8 GB 内存 + AVX2 CPU——旧台式机——得到推理与检索大脑，并如实跳过 LoRA 演化，因为那是 GPU 活（Soup 自己的 CPU 行写着「experimental — very slow」）。两条都达不到：应用照常安装但**不带**本地模型，Settings 卡片说明原因——点名硬件与未达到的门槛——绝不静默省略。

**架构：检索优先，适配器其次。** 按用户微调是脆弱路径；检索是可靠路径。因此本地模型在回答时会把用户**合格**的语料注入为上下文（一个能读取用户工作的「本地大脑」），并在后台用 [Soup](https://github.com/MakazhanAlpamys/Soup)（一条命令，笔记本级 GPU 上的 QLoRA）对用户的合格**风格与偏好**材料训练一个**可选的 LoRA 适配器**作为精修层。能力（工具调用、推理、图像输入）来自**基础模型**；按用户的层贡献的是*内容*与*口味*。把两者分清，就是一个能用的功能与一个自信地编造的功能之间的区别。

**隐私是硬过滤器，不是偏好。** 只有标记为可共享的实体才会被摄取。Context 已经带有 `visibility: local | pending | shared`（`packages/faberloom/context/src/types.ts`）：`local` 与 `pending` 绝不摄取，Memory、Routines、Workflows、Agents 和 Skills 在缺旗标处必须补上（计划的 Fase 3）。一条与我共享的记录可摄取；一条私有的绝不，并且 Settings 卡片会说明跳过了多少、为什么。

**训练门槛：70%，而且用户可以移动它。** 就绪度 = *合格语料被摄取并索引*的百分比，外加一道本地模型必须能用用户自己的数据答对的探针题。默认是 70%，用户可以在同一个 General 行里调高或调低——控件只在开关打开时出现。低于门槛时界面显示「仍在学习」，路由保持默认；到门槛时本地模型接管。70% 是刻意定的，不是随便定的：一个只读了一半证据却自信回答的「本地大脑」，比一个明明白白说没准备好的更糟，而且进度是可见的——但接受更低门槛的用户是明确自己设定的，门槛绝不隐藏。

**路由。** 本地模型以 `provider: ollama`、id `local` 注册。**没有** agent 的 Workspace/Space 或会话在达到门槛后用它，否则用部署的默认路由；携带自己的 provider/model/key 的 agent **永远优先**（路由工作已经交付的那条缝）。本地模型答不上的，通过既有的路由与失败机制交给用户的第三方服务商，并点名原因——用各提供商已有的 quota/invalid-credential 分类。

**仅桌面端。** web/VPS 的行为不变；本地模型不离开用户的机器，它读过的内容不上传。

**是开关，不是安装程序——而且安装程序完全不变。** 安装时不预置任何东西：应用照今天一样快装好、打开，本地模型**不**在其中。Settings → General 的「本地 AI」开关，**默认关闭**，掌管整个生命周期。用户第一次打开它时，Ollama 与模型作为后台作业下载，Settings 卡片显示真实进度——下载百分比，然后安装百分比，然后训练百分比，越过门槛后消失。之后关掉再开，什么也不重新下载：对已有安装做**校验**，而不是重新获取。当硬件不达标时，开关**被禁用**并显示为关，点名硬件与未达到的门槛——在那里它永远无法被打开。

## Proposal

分阶段的工作，每阶段给出其所有者包、交付物与收官证据。阶段按依赖排序；后一个建立在前一个之上，任何阶段没有证据不得交付。

### Fase 0 — 硬件检测与合格判定
- 所有者：`apps/desktop`（若桌面端已有探测模块，则放入 `packages/desktop/hardware`）。
- 交付物：安装程序探测机器（CPU 核心 + AVX2、内存、GPU 厂商 + 显存），并记录带原因的合格判定；应用无论如何都会安装，**且其速度不变**——本地模型绝不属于安装内容。探测是真实可查的事实（`detectHardware()`），不是一次性的，正是它决定 Settings 开关是否可用。
- 证据：覆盖三类（GPU 合格 / CPU 合格 / 不合格）的测试矩阵（每厂商一组夹具），以及不合格机器上的 Settings 开关被禁用并带原因、合格机器上可用。

### Fase 1 — 本地运行时，由开关惰性预置
- 所有者：`apps/desktop` + 一个掌管守护进程生命周期的 `packages/desktop/local-model` 宿主插件。
- 交付物：开关的第一次打开以后台作业预置 Ollama 与模型，Settings 卡片显示真实进度——下载百分比，然后安装百分比——用户除开关外无需任何操作。之后再开启则**校验**已有安装，而非重新下载。若 Ollama 已存在，预置器检测到并直接复用，而不是重装。
- 证据：一个用模拟 HTTP 固定下载与安装进度上报的测试、Settings 卡片渲染每种真实状态，以及再次开启的路径断言为校验而非二次下载。

### Fase 2 — 本地模型成为一等提供商
- 所有者：`packages/faberloom/model-catalog`（+ 选择器列表处）。
- 交付物：`provider: ollama` 通过它自己的 `/v1/models` 进入目录（无需新协议），于是本地模型与其他提供商并列出现在选择器里，分组并带描述，并且有一个路由到它的真实请求被实证。
- 证据：对本地服务器的实时发现，以及一条 spec 证明 provider 为 `ollama` 的请求到达本地服务器且绝不触碰部署方的凭据。

### Fase 3 — 合格语料与隐私过滤
- 所有者：`packages/faberloom/{context,learning,agents,routines,workflows,board}` + `packages/faberloom/knowledge-index`。
- 交付物：每个可摄取实体都带有可见性事实（Context 已有；其余补上），摄取过滤只放行可共享的，并记录跳过了多少、为什么。
- 证据：一条 spec——一条私有 Context/Memory/Workflow 与一条共享的进入管线，只有共享的被索引；Settings 卡片报告跳过数量。

### Fase 4 — 本地大脑（检索 + 门槛）
- 所有者：`packages/faberloom/knowledge-index` + 路由缝。
- 交付物：本地模型以注入的合格语料为上下文作答；就绪百分比与探针题控制路由，且门槛是 **General 里可由用户调整的设置**（默认 70%，只在开关打开时可见）——低于它时界面显示「仍在学习」并走默认；到它时本地模型接管，训练百分比随之消失。
- 证据：一条 spec——本地模型答出一个答案只存在于用户自己已索引数据中的问题、门槛恰好在边界翻转路由、且门槛控件能改变那个边界。

### Fase 5 — 受用户控制的自主演化
- 所有者：`packages/desktop/local-model` + `packages/faberloom/learning`。
- 交付物：Settings → General 的「Local AI」开关，控制演化的开与关；开启时，空闲时循环刷新索引并（用 Soup）重建合格语料上的 LoRA 适配器；关闭时不再训练。开关持久、命名明确，且绝不在用户正在使用机器时运行。
- 证据：一条 spec——切换开关会停止一次已排定的演化运行；Settings 卡片显示上一次演化与下一次排期。

### Fase 6 — 交给第三方服务商的交接
- 所有者：`packages/faberloom/session-agent` + 路由缝。
- 交付物：本地模型答不上的内容交给用户已配置的服务商，并点名原因（既有的 quota/invalid-credential 分类）；交接可见，绝不静默。
- 证据：一条 spec——一个刻意越界的 prompt 被路由到第三方服务商，且 UI 点名了这次交接。

### Fase 7 — 本地模型自己的 harness
- 所有者：`packages/desktop/local-model` + `packages/faberloom/learning`。
- 交付物：负责人要的那套 harness——按用户的评估循环（从用户**合格**数据抽取的一套固定探针）、演化运行的漂移检查，以及每次演化改了什么的日志。正是它让「自主演化」变得可问责，而不是黑箱。
- 证据：评估集绝不在私有记录上训练（有断言），且每次演化运行都记录改动与探针结果。

## 训练器：Soup

训练用 **[Soup](https://github.com/MakazhanAlpamys/Soup)** 完成——Apache-2.0 的微调 CLI。选它是因为计划需要它，而不是图省事：一份 YAML 配置、一条 `soup train` 命令、笔记本级 GPU 上的 QLoRA，以及这里真正承重的 **layer streaming**：冻结的基座不进显存，按解码器层逐层喂入，于是一张 4 GB 的笔记本 GPU 就能训练一个 8B 模型（他们自己公布的记录：RTX 3050 4 GB，119.6 tok/s，峰值 3.32 GB）。我们默认的是 3.8B 的 LoRA，远在其内。

它给本计划的东西：`soup init --template chat` 出配置、`soup train` 跑训练、现成的菜谱与硬件适配表，以及它自己的探针与评估门——本地模型的 harness（Fase 7）就建在这些之上。基础模型以 GGUF 拉给 Ollama，而 Soup 的 `soup export --model … --format gguf` 正是适配层与运行时会合的方式。它的已知约束也有意带着：仅 Python 3.10–3.12，且需要 `[train]` extra。

它**不**用来做什么：检索大脑（Fase 4）——索引无需任何训练就能回答新数据。Soup 在演化（Fase 5）时才登场，不在答题时。

## Alternatives considered

**用 LM Studio 作运行时。** 它 GUI 优先，没有无人值守的安装或模型管理路径——一个从不打开它的用户永远也得不到本地模型。Ollama 是无头守护进程，生命周期可脚本化，API 与 OpenAI 兼容；唯有它能让安装程序预置、让 harness 管理，而不需要用户动手。

**把按用户微调当作主机制。** 原始诉求是「在用户数据上训练」，但按用户微调很脆弱（需要精选语料、逐用户又慢又贵、可能静默漂移），而且对新数据**不**立即作答——必须重训。检索对新数据立即作答并如实交代证据；LoRA 适配器再在微调真正有价值的地方加上口味层。检索优先，适配器其次。

**一个小模型同时做工具、推理和视觉。** 没有任何 4B 以下的模型能三者兼得。这样承诺只会交付一个工具调用出错或读错图像的模型。基础模型是文本 + 工具；视觉是硬件放得下时的可选变体。

**更低的训练门槛（50%）。** 一个只读了一半证据却自信回答的本地大脑，比一个明明白白说没准备好的更糟。70% 是刻意的门槛，而且进度是可见的。

**把整个功能都挡在 GPU 之后。** 无独显的笔记本很常见，3.8B 的 Q4 模型能在上面作答，只是慢。把它们排除会挡住大多数用户；慢路径是诚实且可用的。

## Acceptance criteria

- 安装不变且快速；「本地 AI」开关默认关闭、在跑不动的硬件上被禁用并带原因，首次开启在后台预置 Ollama 与模型，下载/安装/训练百分比可见。
- 本地模型以 `provider: ollama` 出现在选择器中，且一条路由到它的请求到达本地服务器、绝不触碰部署方的凭据。
- 本地模型用用户的合格数据作答；私有的 Context/Memory/Workflow/Routine/Skill/Agent 绝不被索引或训练。
- 70% 门槛控制路由，进度与「仍在学习」状态可见。
- Settings 开关能启动也能停止演化；每次演化都被记录并被探针检验。
- 本地模型答不上的 prompt 交接给用户的提供商并点名原因。
- web/VPS 的行为不变。

## Risks

- **按用户微调可能静默漂移。** 缓解：harness（Fase 7）用固定的合格探针集检验每次演化运行并记录改动；漂移的运行被回滚，不保留。
- **隐私过滤是承重缝。** 漏掉一个可见性旗标就会把一条私有记录泄进训练。缓解：过滤集中在一处，且用一条测试（而非约定）断言摄取管线拒绝私有记录。
- **小模型过度承诺。** 缓解：如实说明基础模型的能力（文本 + 工具；视觉可选），答不上的内容交接并点名原因。
- **以 Windows 为先的检测。** 硬件探测必须覆盖各 GPU 厂商的驱动并提供无头回退；探测失败绝不让安装程序阻塞（降级为「不合格」并给出原因）。
- **web 不得继承。** 该功能只挂到桌面组合；若一个旗标漏进 web 包，就会试图运行一台并不存在的本地模型。
