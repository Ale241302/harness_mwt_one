# Agent Note: 把网关会话桥接到操作者自己的电脑

Status: proposed

[English](2026-10-14-gateway-session-on-the-operator-computer.md) | 中文

## Problem

桌面端只启动一个后端，而两个选项各自只覆盖操作者想要的一半。网关会话展示共享界面（Space、分享、控制台、产品 MCP 服务器），其 Workspace 是部署上的文件夹，操作者自己的磁盘因此不可达。本机会话可达操作者的文件夹，而共享数据仅限于经 `faberloom-shares` 传递的部分，因此两处安装展示不同的 Space 与不同的会话。既要在自己的文件上工作、又要共享界面的操作者无法同时得到两者，产品自己的界面也这么说。

harness 早已在此所需之处把执行与呈现分开：客户端通过 Typert 远端协议与 Host 对话，Host 通过可替换的提供者读写并运行进程。`ctx.fs` 是一个拥有多个实现的接缝（[文件系统包](../../implemented/architecture/2026-09-05-workspace-files-service.zh.md)），执行世界可跨消费者移植（[可移植执行世界](../../implemented/architecture/2026-07-28-portable-execution-world-consumers.zh.md)），而 SSH 家族已经能说一个真实的远端世界（[POSIX SSH 运行时](../../implemented/architecture/2026-09-11-posix-ssh-runtime.zh.md)）：`@deepseek-ai/dsh-fs-ssh`、`@deepseek-ai/dsh-subprocess-ssh`、`@deepseek-ai/dsh-sandbox-ssh` 与 `@deepseek-ai/dsh-terminal-ssh`。产品中没有任何东西为操作者自己的电脑组合它们，也没有任何东西登记那台电脑。

## Proposal

**网关会话通过一条出站隧道触达操作者电脑上的一个目录，作为部署挂载的执行世界。** 浏览器窗口仍是 `harness.mwt.one` 的客户端，因此前端或后端改动仍随服务器部署生效，而操作者自己的文件夹在共享产品内变得可用。

需要四件东西，按此顺序。

1. **传输。** 操作者的电脑向外拨号，部署从不向内拨入，因此操作者不需要公网地址、不需要路由器端口转发、部署也不需要入站规则。最小的版本是指向部署的 OpenSSH 反向远端转发（`ssh -R`），因为仓库已经用 OpenSSH 驱动多路复用会话与终端；若 `ssh -R` 过于狭窄，WireGuard 中枢或一条小型双向 TLS 隧道是替代方案。
2. **提供者。** 网关的按用户组合针对该隧道端点挂载 `dsh-fs-ssh`（并按世界所需挂载 subprocess、sandbox 与 terminal 行）。密钥材料与主机校验按用户经凭据接缝与环境到达，绝不写入生成的 patch，这是产品 MCP 行已经遵循的规则。
3. **根。** 操作者注册的 Workspace 必须是远端世界里的路径。`workspace.create` 会规范化路径、要求目录存在并存储它；注册表要么通过已挂载的提供者解析，要么由部署把远端世界呈现在一个稳定路径上，使现有注册表照常工作。
4. **选择器与策略。** 会话的目录流程必须列出操作者的电脑而不是容器（在操作者电脑上运行原生选择器并上报所选路径，或者由浏览后端经同一条隧道列出），而部署需要操作者能够采取行动的策略：智能体可读哪些根、进程世界是否受限，以及操作者如何撤销该连接。

此时产品的两个界面只差一句话：同一个会话，文件夹在操作者的电脑上而不是部署里。

## Security

部署获得了一条通往并非自己所有的电脑的路径，而这正是本次改动的全部风险，因此在收益之前先陈述：

- **密钥按操作者持有，并可在控制台撤销。** 隧道的密钥属于操作者，部署只保存公钥的一半，撤销是一次能停下该世界的控制台操作。没有任何共享密钥能授权一台机器。
- **世界由策略限定，而不是由隧道限定。** `dsh-sandbox-ssh` 与限制行决定进程在远端能触及什么（[POSIX SSH 运行时](../../implemented/architecture/2026-09-11-posix-ssh-runtime.zh.md)）；操作者授予的根就是选择器列出的根，也是文件工具接受的根。
- **操作者能看到该连接并在本机停止它。** 在操作者电脑上关闭隧道会在下一个请求处结束该世界，无需触碰部署。
- **数据属于操作者。** 远端 Workspace 是一条路径而不是副本：部署的存储保存会话日志与派生索引，文件字节留在操作者的电脑上。

## Alternatives considered

**保留两个大脑，让操作者自己拷文件。** 这正是产品今天的行为，也是本条笔记存在的原因：一个后端上的 Workspace 不会出现在另一个上，副本会分叉。

**在本机 Host 上提供部署的前端，让本机模式跟随 web。** 前端、Host API 与插件图是一个经过整体验证的组合，来自另一个版本的前端会遇到它不是据此构建的 Host。[打包笔记](../../implemented/architecture/2026-08-25-electron-desktop-packaging-and-updates.zh.md)记录了那一发布身份，桌面端 README 陈述了其后果。

**在操作者的文件夹与部署的文件夹之间使用文件同步工具（Syncthing、Dropbox、双向 rsync）。** 它搬运字节而不是搬运世界，因此每次并发编辑都需要冲突解决，部署的副本会无界增长，而且两侧都无法在对方的目录里运行进程。

**从部署反向 SSH 到操作者的电脑。** 它需要一个部署能到达的地址，每次安装都要配置 NAT 与防火墙，并要求操作者暴露一个监听端口，严格劣于向外拨号。

**把整个 Host 搬到操作者的电脑上，让共享界面成为它的客户端。** 它把共享数据的所有权倒置，于是 Space、分享、控制台与产品 MCP 服务器都必须能从操作者拥有的 Host 到达，并且要求部署去服务一个其后端已不受自己控制的客户端。

**用一套新的远端文件协议代替 SSH 家族。** `dsh-fs-ssh` 已经在一条传输上承载读取、写入、列表、进程、终端与沙箱，其行为与失败方式都有文档；第二套协议会把这一切重新推导一遍并分裂覆盖。

## Acceptance criteria

部署中的一个 `dsh` 经隧道读取、写入并列出测试电脑上的一个目录，并在此运行一条命令，且该电脑没有任何入站端口。以该路径注册的 Workspace 支撑一个会话，其 `@` 浏览器、文件工具与终端都在操作者的电脑上解析。操作者的控制台显示该连接并可撤销，撤销在一个请求内停下该世界。

本次 spike 不包含：对远端世界的记忆与知识索引、每位操作者多台已登记电脑、产品内的登记界面，或把已有的本机会话迁移到桥上。

## Risks

- **支持成本。** 隧道后的世界会以本机文件夹不会有的方式失败：隧道断开、笔记本休眠、密钥轮换、不同的 shell。每一种都需要操作者能据此行动的诊断，而那是以周计的产品工作，不是一个开关。
- **安全。** 部署可以在授权策略内于操作者的电脑上运行进程。设计以按操作者的密钥、撤销、显式根列表与远端限制来回答这一点，缺少任何一项都不应交付。
- **两个世界，一个会话。** 世界为远端的会话必须在每个出现路径的地方明确说明，否则操作者会以为自己正在编辑部署上的文件。
- **顺序。** 这是桌面端计划中最大且最不可逆的一项。它必须在本机 harness 完成之后才开始，因为本机模式是今天就能让操作者的文件可用的东西，而桥是让这些文件与共享界面同时可用的东西。
