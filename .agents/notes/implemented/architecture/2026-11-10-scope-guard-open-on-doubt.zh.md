# Agent Note: 范围守卫只拒绝被确认为个人的请求

Status: implemented

[English](2026-11-10-scope-guard-open-on-doubt.md) | 中文

## Problem

[2026-11-02 的笔记](2026-11-02-byok-composition-shared-key-guard.zh.md)交付的守卫拒绝每一个分类结果不是已确认 `work` 的回合：`scopeFallback` 默认 `refuse`，`work` 判定需要 0.80 置信度，且第二次以相反问题措辞的调用也必须回答 `work`。三条规则合在一起，把分类器的犹豫变成了用户无法处理的拒绝。一个 B2B 账户问“dame información de la 2487-2026”，下一条又问“de esta PO 505244”——一个是案件号，一个是采购订单号，正是这些用户指称记录的最短方式——两次都收到“No pude verificar si este pedido entra en el alcance de la llave compartida de FaberLoom”，完全没有答案。

分类器没有任何对话：它只看到一行文字、一个裸号码，除了 Space 标题之外没有 Space 上下文。它以低置信度作答，0.80 的门槛把这一犹豫变成了拒绝。分类器调用失败时、运行在推理路由上而 64 token 预算在写出任何 JSON 之前被隐藏 token 耗尽时，以及确认调用给出不同答案时，出现的都是同一个拒绝。

## Decision

守卫现在只拒绝分类器明确判为个人的请求。由此产生三条规则。

只命名一条业务记录的消息就是工作，无需模型调用即作出判定。`isWorkReference` 读取一至八个 token，由前置的提问或虚词、记录名词（`pedido`、`expediente`、`caso`、`PO`、`PF`、`OC`、`SAP`、`factura`、`proforma`、`contenedor`、`guia`、`envio`、`tracking` 等）以及至少一个标识符组成——一个号码，或一到四个字母前缀之后的号码，如 `2487-2026`、`505244`、`PF-1234`、`OC/1234`。其他任何内容都不成立，因此 `poema 505244`、`hacé la tarea 12` 和 `necesito el estado del pedido 505244 de Sondel` 仍交由分类器。通过该规则的回合不携带个人请求可用的内容：模型只能去查这条记录。

`scopeWorkConfidence` 默认 0.50，并同时约束两个方向。达到或超过它的 `personal` 判定用个人拒绝文案拒绝；低于它的答案只是犹豫。达到或超过它的 `work` 判定在确认调用之后花掉共享密钥，而该处只有确信的 `personal` 答案才拒绝——第二次调用是对伪装的检查，不是第二次否决。低于门槛的 `work` 判定同样是犹豫。

`scopeFallback` 默认 `allow`。分类器不可用、不可读或被截断时，回合照常通过。产品工具掩码与 Space 范围仍然生效，因此这样的回合只能触达 MWT.ONE、SICOP、账户邮箱与该 Space 的文件，别无其他；部署承担的风险是一个提示词的 token。`DEFAULT_UNVERIFIED_REFUSAL` 仅用于没有人类文本的回合，`scopeGate` 在任何分类器调用之前就拒绝这种回合。

两次分类器调用都会在当前回合之外读取上一人类回合，放在独立的 `<previous>` 元素中作为数据，因此片段在它所延续的对话里被判断。每次调用获得 512 个答案 token 而不是 64 个，这正是推理路由在写出 JSON 对象之前所需的空间。

## Consequences

- 查询一条记录的答案是单次供应商调用：没有分类器延迟，没有分类器成本，也不依赖模型判断一个裸号码。
- 分类器变慢、被限流、超出预算或用散文作答时，守卫不再阻断业务工作。代价是分类器不可用期间个人请求会通过，由产品工具掩码限定其可触达范围。
- 介于 0.50 与 0.80 之间的个人判定现在会拒绝，而在旧门槛下它只会被当作“无法核验”；低于 0.50 的个人判定现在会通过。两者遵循同一规则：门槛决定什么算判定，犹豫不构成拒绝。
- 确认调用现在只增加延迟，不再有权单独拒绝一个 work 回合；部署可以通过 `scopeConfirmProvider` 与 `scopeConfirmModel` 把它放到更便宜的路由上。
- 每个 `work` 回合仍然花费两次分类器调用。work 判定之后的续接 token 仍然跳过这两次调用。
- 守卫的残余缺口没有变化：两次答案都把个人请求判为 `work` 仍是模型错误，而一次错误答案同样不再足以拒绝一个业务回合。

## Alternatives considered

**保留故障关闭的回退，只提高分类器预算。** 它修复被截断的答案，却对裸案件号上的低置信度判定毫无作用——而那正是被报告的案例。拒绝它的是门槛，不是预算。

**在分类器指令里增加更多业务词汇。** 词表快速通道是被刻意删除的；一份词表本身就是构造上的绕过，下一种记录格式就会漏掉。确定性规则匹配的是 token 类别——号码及其前缀——而不是名词词表。

**把门槛降到 0.50 并保留确认否决权。** 无法作答的确认仍然会拒绝，因此一个正常的第一答案加上一次退化的第二次调用仍会阻断回合。确认现在只在其明确不同意时拒绝。

**只限制工具面，让每个提示词都通过。** 那会取消守卫存在的理由：即使不运行任何工具，个人答案也会花掉部署的 token。值得保留的正是明确的 `personal` 判定。

## Testing

`packages/faberloom/session-agent/tests/policy.spec.ts` 覆盖 `C-B02.12`：可接受的记录引用形式、被拒绝的个人形式，以及携带上一回合的分类器问题。`tests/session-agent.spec.ts` 覆盖守卫：记录引用在不调用分类器的情况下通过、低于门槛的 `personal` 判定通过、低置信度 `work` 判定花掉密钥、分类器不可用时默认放行并在 `scopeFallback: 'refuse'` 下拒绝、不可读的答案从不被当作个人、确认回答 `personal` 时以个人文案拒绝、续接记忆，以及自有密钥路径。包内测试套件：115 个测试，`tsc` 与 `oxlint` 为零。
