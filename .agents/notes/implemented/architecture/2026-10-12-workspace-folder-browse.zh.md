# Agent Note: 从 `@` 菜单浏览工作区文件夹

Status: implemented

[English](2026-10-12-workspace-folder-browse.md) | 中文

## Problem

在输入框中键入 `@` 时，菜单最多列出 20 个来自模糊索引的工作区文件，而该索引以会话的工作目录为根。在真实项目文件夹里，这个索引无法触及任意文件，也从不展示文件夹结构，因此想把模型指向用户自己文件夹里看得见的某个文件，唯一办法是手打路径。宿主此前已经向浏览器暴露了受限的目录列表，触发器菜单也已经支持钻入某个候选并沿面包屑返回；只是没有任何东西把两者接起来。

## Decision

**`@` 的文件部分一次浏览一个真实目录。** `packages/client/ui-reference` 现在用 `ctx.remote.workspaceFiles.list(sessionId, path)` 构建文件候选，即宿主那条限定在会话工作区根内的列表；对产品 Space 而言，该根就是用户采纳的那个文件夹。包含路径分隔符的查询会浏览该目录，并按键入的片段过滤其子项；只输入 `@` 则列出工作区根。不含分隔符的查询保留模糊索引，因此键入名称仍然在整个工作区中搜索。一个区块，两种模式，由用户是否键入路径决定。

**复用列表，而不是重建。** 目录排在文件之前，行的图标区分两者，文件夹行可钻入，菜单的面包屑可返回；宿主截断的列表会明说，而不是隐藏条目；宿主的每一种错误（`outside-workspace`、`not-found`、`not-directory` 等）都会渲染出可读的一行。选中文件后插入与此前相同的 mention 文本（`formatFileMention`），因此 mention 仍是纯路径文本，模型读它、宿主也以同一个根解析它。

**web 与桌面同样可用，但有一条架构限制。** 两者都是同一个客户端对着一个宿主运行，而桌面上该宿主是本地进程并带原生文件夹选择器，因此用户自己的文件夹在桌面上可达。web 应用选择的是宿主上的目录，而不是访问者机器上的目录，本次改动没有改变这一点：让 web 读到访问者自己的磁盘需要另一套机制，而不是调整列表。

## Alternatives considered

**新增第二个列出文件的 `@` 来源。** 现有来源已经拥有 `@` 分组、钻取管线、图标、mention 语法与会话行。第二个文件来源会让同一个菜单里出现两个内容不同的文件区块，用户无法分辨哪一个才是浏览，因此改为替换文件那半个来源。

**把模糊索引重新指向工作区根。** 模糊索引回答的是「帮我找这个名字」，而这里的要求是「把这个文件夹显示给我」。把索引改成递归也得不到可浏览的树，还会丢掉只剩名字时理应保留的整库廉价搜索。

**新建一个树服务。** `workspaceFiles.list` 已经自我限定在工作区根内、已经报告截断、也已经为自己的失败命名；并行实现必须把这一切重新推导一遍。

## Consequences

用户现在可以从输入框触达该 Space 文件夹里的任何文件，包括模糊索引 20 条上限所隐藏的文件，模型收到的是真实路径。`@` 菜单有了唯一的浏览方式和唯一的搜索方式。代价是浏览受宿主单次列表上限（2000 条）约束，并限定在工作区根内，因此根之外的文件夹仍不可达，web 应用也仍无法列出访问者的本地磁盘。从 `@` 菜单读取之后再编辑、删除或附加工作区文件属于另一项改动，而变更的那一半已在它自己的界面上交付：`packages/api/workspace-files` 在读取动词之外新增 `createFile`、`createDirectory`、`move` 与 `remove`，每个动词都通过与读取相同的文件系统解析路径，并拒绝会话工作区根之外的目标，每个动词都以读取已声明的带类型拒绝码作答（`not-found`、`outside-workspace`、`too-large`、`already-exists`、`directory-not-empty`、`root-refused`、`symlink-refused`、`bad-target` 与 `unsupported-backend`）；`createFile` 原子地写入一个 UTF-8 文件且从不覆盖，`createDirectory` 创建一个目录并补齐缺失的父目录，`move` 重命名或移动一个条目，除非传入 `{ overwrite: true }`，否则拒绝已占用的目的地，而 `remove` 删除一个文件或一个空目录，除非 `{ recursive: true }` 连同内容一起删除，否则拒绝仍有条目的目录。`packages/faberloom/tool-faberloom` 以 `faberloom_files_create`、`faberloom_files_rename` 与 `faberloom_files_delete` 把同一能力暴露给模型，而 `packages/client/ui-sidebar-files` 的树获得了该手势：表头的新建控件在工作区根中创建，目录行的更多操作菜单在重命名与删除之上加入两个创建手势，删除会打开一个确认框，指名该条目并提供连同目录内容一起删除的复选框。按路径附加文件仍未交付：今天的附件是被上传的副本，而不是工作区路径。

验证：该包的 29 条客户端测试通过，覆盖率 100%，覆盖根列表、钻入子目录、面包屑、目录先于文件、截断提示、四种错误、无分隔符查询仍走模糊索引，以及选中后产生的 mention 文本。
