# 代理笔记：调度器自行执行的每日运行上限

状态：已实现

[English](2026-11-23-daily-execution-limit.md) | 中文

## 问题

调度器启动工作时没有自身的上限。一个被错误配置为每分钟运行的例行程序，或者一个持续产生触发事件的邮箱，会在无人察觉的情况下消耗供应商预算和队列容量；唯一的信号是事后每条失败产生的复核行。E1 包还欠持久的计数分母：系统自己做了什么、留给人做了什么、什么失败了，并发布到面板和网关已经读取的位置。

## 决定

### 上限是配置字段，不是常量

`maxRunsPerDay` 与 `ownerId`、`enabled`、`intervalMs`、`alertWindowMs` 并列。零或缺失表示无上限，因为没有选择数字的部署就是没有选择；隐藏的默认值要么停止真实工作，要么承诺一个守不住的边界。

### 计数属于当天，不属于进程

`<DSH_HOME>/faberloom-usage.json` 以 UTC 日期为键保存 `{ day, runs }`。重启、第二个进程或重新部署都不得给所有者第二份预算，而重置不需要自己的调度器：另一天的账本读作零。只统计已启动的运行，因此去重到既有执行的批次不消耗额度。

### 到达上限是通知，绝不是邮件

批次返回 `skipped = "daily execution limit reached (n/max)"`，不启动任何工作，并按天去重发布一条 `usage-limit` 通知。通知说明什么停止了、进行中的工作会继续、以及如何修改上限。用邮件宣告自己的上限会违反“不发送任何自动消息”的规则。

### 分母与其所有者一起发布

`faberloom-metrics.json` 包含 `totals`、`denominators` 和 `usage`。`denominators` 命名自主性计数——`autonomyRuns`、`awaitingPerson`、`failed`、`unknownResult`——并有意识地不混入所有者自己的操作。`unknownResult` 在这里为零，因为不确定的发送结果属于邮件尝试账本，而不属于调度器；该字段存在是为了让面板只读一种结构。

### 不设并行事件总线

提案、批准、更正和丢弃已经是持久的看板行，每次状态变化都有审计事件。同一批事实的第二本账会两次拥有同一份数据，并在月度报告中重复计数。缺少的是上限和发布的分母，而不是另一份记录。

## 考虑过的替代方案

**用令牌或货币预算代替运行计数。** 本切片拒绝：每个代理的 `BudgetPolicy` 已经限制一次执行的花费，而聚合货币上限需要调度器并不拥有的单次运行价格。

**通过暂停例行程序来停止。** 拒绝：暂停会重写所有者的配置，所有者必须逐一手动重新激活。上限必须明天就能撤销，而不触碰他们的例行程序。

**只在日志中发布上限。** 拒绝：面板和网关已经读取同一个指标文件，没人看得见的上限就是没人信任的上限。

## 后果

会风暴的例行程序自行停止，并且每天说明一次。想要不同节奏的部署修改一个字段。计数是一个文件，因此没有写权限的主目录会退化为进程内计数，而不是让批次失败。

## 测试

`vitest run packages/faberloom/execution/tests` 通过 40 个测试。新增覆盖：两个批次各启动一次执行，第三个返回跳过原因，带一条通知，指标中 `atLimit: true`；当天计数在 `faberloom-usage.json` 中持久，之后的一天重置；未配置上限时永不阻塞、永不发布。
