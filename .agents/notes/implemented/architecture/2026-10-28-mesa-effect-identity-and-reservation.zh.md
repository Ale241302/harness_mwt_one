# Agent Note: 一个效果键、一份预留、一个窗口

Status: implemented

[English](2026-10-28-mesa-effect-identity-and-reservation.md) | 中文

## 问题

看板可以在效果发生之后记录它；发送之前没有任何东西决定它是否允许发生。

`recordEffect` 接受任何带授权名的 `APROBADO` 条目，`complete` 接受任何已批准的条目。

两者都不认识 `effect_key`，所以都无法拒绝同一意图的第二次执行。

15 分钟窗口此前无处安放：没有可推迟的已记录意图，也没有可回退的状态。

存储排除了显而易见的修法。

`boardDomainSpec` 是带模式校验的键值域：一条记录一次持久写，没有跨表事务（ADR-001）。

它也没有二级索引。

把预留作为第二次 `put` 写在批准旁边，就是两次提交。

`CONTRATO_EFECTOS_MESA.md` 签下了公式、四个预留状态、15 分钟窗口、发件箱和核对规则。

SPEC §10.1 把公式和按目的地的幂等性留空。

本备忘钉住实现者仍会弄错的四点：组成部分的写法、记录的所在、时钟、以及与目的地的边界。

## 决定

**只有一个函数生成 `effect_key`，每个组成部分在哈希之前先规范化。**

`effectKeyOf` 就是那个函数，其他任何代码路径都不得生成键：

```text
effect_key = sha256(tenant_id + ":" + action_type + ":" + destination + ":" + business_key + ":" + artifact_hash)
```

### 五个组成部分

| 组成部分 | 规范化 | 换一种写法会 |
|---|---|---|
| `tenant_id` | 条目的 `companyId`，按预留键的写法书写 | 把一个效果挪进另一个租户 |
| `action_type` | 调用方给的动作类型，去空白 | 把 `Mail Send` 当成第二个效果 |
| `destination` | 邮件列表小写、拆分、去重、排序；其他去空白后照原样 | 按收件人顺序给同一封邮件各生成一个键 |
| `business_key` | 条目的 `businessKey`，绝不用条目 id | 把竞争这一情形删掉 |
| `artifact_hash` | 已批准版本的哈希 | 把一个版本散列成两个键 |

`tenant_id` 是条目的公司，绝不是调用方的。

没有公司的部署沿用预留键已在用的 `sin-empresa` 哨兵值，所以两个键指向同一个租户。

残余风险是一个真名叫 `sin-empresa` 的租户；那需要新公式，不是第二个哨兵值。

`action_type` 去空白后按原样使用。

目前没有任何东西拒绝第二种写法，所以 `Mail Send` 和 `mail.send` 会为同一个效果生成两个键。

目的地是邮件列表，当动作类型以 `mail.` 开头或值里含 `@`。

该列表依次去空白、小写、按逗号或分号拆分、去空项、去重、排序。

空白不是分隔符：`a@x b@y` 与 `a@x;b@y` 是两个键，所以调用方只能写两种被接受的分隔符之一。

其他目的地在去空白后照原样使用外部 id，因为看板无法核实某个系统的字母大小写规则。

`business_key` 没有退路：没有它的条目以 `EFFECT_IDENTITY_INCOMPLETE` 被拒绝，绝不用条目 id 顶上。

键里放条目 id 会让每个条目都唯一，竞争这一情形就整个消失。

`artifact_hash` 是 `approve` 已经绑定到已批准版本的那个哈希，从条目读出。

效果代码不再对载荷哈希一次，所以一次接受和它的效果不可能指向同一份文档的两个版本。

各组成部分用 `:` 拼接，而没有任何东西拒绝含有它的组成部分。

因此一个带冒号的业务键可以让两个不同的元组共用同一个字符串；要堵住它需要 D-12 下的新公式，不是转义。

**同一执行的重试保留键。**

`execution_id` 不是组成部分，所以重试从同一条目重新导出同一个键并找到自己那一行。

幂等键只存一次，默认是 `effect:<effect_key>`；每次重试复用它。

按尝试生成键会把一个效果变成 N 个。

**新的制品版本不参与竞争。**

`artifact_hash` 变了，键就变了，旧的活预留不会拒绝这次新执行。

旧条目在它的预留结算之前一直封锁（契约 §1），所以结果未知时不会重发。

**同一业务与同一制品的两个条目是竞争者。**

键不携带条目 id，所以第二次接受解析到第一个条目持有的那一行。

只要那一行是 `RESERVADA` 或 `DESPACHADA` 就以 `EFFECT_TAKEN` 被拒绝，`admin_close` 之后也一样（W-84）。

竞争的单位是键，不是条目。

### 三处所在

**条目记录决定，预留和消息是由键寻址的行。**

`approveWithExecution` 在按租户的 `serial` 段里运行，动手之前先检查活预留。

然后它把 `effect_reservations` 和 `effect_outbox` 写在 `<tenant>:<effect_key>` 之下，再提交条目。

如果那次提交抛错，同一段里取消消息并释放预留。

动作类型有窗口时条目落在 `DELEGADO_EN_VENTANA`，没有窗口时落在 `EJECUCION_PENDIENTE`。

条目保留 `effectKey`、`reversalDeadline` 和 `executionOutcome`；`pruneEffects` 只碰那些行。

用行而不是字段，因为竞争者和消费者都只拿着键、手上没有条目。

以该地址为键的行，是这个存储唯一提供的按键查找。

代价是一次接受是三次写入。

在预留写入与条目提交之间崩溃，会留下一行条目从未记录过的 `RESERVADA`。

它自己的执行在重试时修复它，因为接管守卫只拒绝另一个执行。

该键的其他任何接受都被拒绝，而 `pruneEffects` 只删已结算的行，所以这个键一直被占着。

**键由预留行本身声明，不是由索引声明。**

每个 `<tenant>:<effect_key>` 一行：表键就是声明，也就是 routines 域为 `event_keys` 使用的先声明再写入的形状。

SPEC §10.1 写的是部分唯一索引，这个存储建不出来。

`claimKey` 不能照搬：它在持有条目非终态时拒绝，而这里的拒绝要跟着预留走。

把声明搬离那一行会带来三种失败。

没有按租户的段，两次接受都会读到没有行，然后都写入，也就是一个键两份预留、W-96 失效。

用内存映射代替行，重启会忘掉声明，崩溃会重新打开每一个效果。

把声明放进第二张表，行与声明可以互相矛盾，而没有东西说得清哪一个在拒绝竞争者。

**消费者在发出之前核实。**

`dispatchEffect` 需要一条 `PENDIENTE` 且可派发的消息、一个 `EJECUCION_PENDIENTE` 的条目，以及一份 `RESERVADA` 的预留。

预留必须写明消息的执行与条目。

在此之前它先执行窗口：仍活着的 `DELEGADO_EN_VENTANA` 条目返回 `WINDOW_OPEN`，已过截止时刻的先把条目过期。

任何一项失败，它取消消息、释放预留，并返回一个写明原因的拒绝（契约 §2.6、W-102）。

之后它先把消息置为 `DESPACHADO` 再调用适配器，所以声明之后的崩溃不会把效果发两次。

把检查搬进生产方，就变成了对过去的检查：重新校验、回退和替换都会释放预留。

在接受的时刻就决定发送的发送方，发出的正是 W-102 禁止的那个效果。

### 两个时钟，各自只发生一次转换

**窗口是推迟，不是竞速。**

截止时刻在接受时按 `effectReversalWindowMs` 打上并持久化在条目上：`mail.send` 为 15 分钟。

金钱、库存和发运默认没有窗口，因为 CEO 签名取代了它（D-12）。

在它之前不得发出任何东西，所以窗口内的回退不会输给手快的发送方；消费者是等着，而不是提前发。

截止时刻是存下来的瞬间，不是派发时读的配置，所以之后再改映射也移动不了已有的窗口。

没有窗口的动作类型不记录截止时刻，条目在接受时直接进入 `EJECUCION_PENDIENTE`，不提供回退。

**回退和到期各自只走一次，且只决定一次。**

`revert` 需要一个截止时刻仍在未来的已委派条目；`expireWindow` 需要截止时刻已过。

两者都在按租户的段里运行，所以后到的一方看到先到者写下的状态。

被回退的效果不会后来到期进入派发，已到期的也不会被回退（契约 §3）。

回退在同一次段里清空 `effectKey`、取消消息、释放预留。

`revalidateEffect` 对派发之前失败的控件走同一条规则。

条目回到 `PENDIENTE_CRITERIO`，消息被取消，预留被释放，所以同一效果的新批准能通过（W-95）。

### 与目的地的边界

**看板决定身份、预留、窗口和核对。**

它拥有 `effect_key`、那两行、四个预留状态、截止时刻、消息状态，以及每种结果对应的转换。

`CONFIRMADO` 到达 `EJECUTADO`，`FALLIDO` 到达 `ERROR_RECUPERABLE`，`DESCONOCIDO` 停在那里。

`CONCILIADA` 和 `LIBERADA` 是终态，`adminClose` 关闭条目而它的预留保持 `DESPACHADA`（W-65）。

迟到确认会举起一行告警、留下 `effect.late_confirmation` 审计，并且不重开条目（W-85）。

**目的地是否幂等，由适配器决定。**

`BoardEffectAdapter.idempotent` 是这个事实唯一的所在；契约按目的地把它留空，本备忘不作决定。

`retry` 在适配器没有声明 `idempotent: true` 时拒绝 `DESCONOCIDO`，所以没有声明就只有 `reconcile`。

看板从不按动作类型或目的地字符串推断幂等性。

对非幂等目的地重试，会复制一个两侧都无法撤销的效果。

### 本备忘之后禁止

1. 第二个键公式，无论在适配器、控制台任务、MCP 接口还是测试辅助里。一个函数，一种写法。
2. 按租户 `serial` 段之外的接受，或不是由 `approveWithExecution` 写入的预留。
3. 没有消费者检查的派发：不从接受路径发出，也不设绕过它的已核实快路径。
4. 释放预留的 `admin_close`。它关闭条目；预留在核对之前保持 `DESPACHADA`。
5. 对尚未声明自己幂等的目的地做 `DESCONOCIDO` 的 `retry`，或在截止之后接受回退。
6. 通往 `EJECUTADO` 或记录效果的第二条路径：`complete` 和 `recordEffect` 早于预留。

## 考虑过的替代方案

**把预留和消息做成条目记录上的字段。** 一次 `KvTable.update` 会同时容纳状态变更、审计事件、预留和消息。

它输在竞争者和消费者都只拿着键、手上没有条目，所以无论如何都需要一行按键寻址的记录。

两者都留就是同一事实的两个来源，只留字段则每次接受都要扫一遍。

**在 `effect_key` 上建部分唯一索引。** 那是 SPEC §10.1 写的东西。

它输在这个存储没有二级索引，也没有 insert-if-absent；唯一的唯一键就是表键。

**在生产方核实、从接受路径发出。** 它去掉了消费者和延迟。

它输在预留可能在接受与发送之间被释放，而那正是 W-102 禁止的情形。

**从条目 id 导出键。** 它天生唯一，不需要规范化。

它输在描述同一个效果的两个条目永远不会竞争，W-84 的拒绝就无法发生。

**让每个目的地适配器生成键。** 适配器最清楚自己目的地的写法。

它输在两个适配器会把同一个效果生成两个键，看板就再也不能拒绝竞争者。

## 后果

- 三张新表：`effect_reservations`、`effect_outbox`、`effect_alerts`，以及三个默认 null 的新条目字段。
- 已有的行照常加载，因为每个新字段都默认为 null，域版本仍是 1。
- 看板在第二次发送之前拒绝竞争者，让回退不参与竞速，并在重试时不生成新身份。
- 租户隔离是行键：没有键跨过 `companyId`，所以另一个租户的预留永远不会被读到（契约 §2.7）。
- `pruneEffects` 删除超过 `effectRetentionDays`（90 天）的已结算行；活预留和未结算消息永不清理。
- 一行孤儿 `RESERVADA` 会一直占着它的键，直到它自己的执行重试；没有命令能结算一行条目从未记录过键的预留。
- `complete` 和 `recordEffect` 仍能在没有预留的情况下到达 `EJECUTADO` 并记录效果，所以 W-84 和 W-96 在那两条路径上不成立。
- `action_type` 没有封闭集合，含 `:` 的组成部分不被拒绝；两者都是公式层面的缺口，不是规范化选择。
- 证据是 `CONTRATO_EFECTOS_MESA.md` §6：九个用例，覆盖 W-84、W-95、W-96、W-102。
