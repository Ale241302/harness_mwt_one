# Agent Note: A Google model that cannot disable thinking gets its lowest accepted level

Status: implemented

English | [中文](2026-10-23-gemini-thinking-level-floor.zh.md)

## Problem

A session switched to `google/gemini-3.8-flash` failed on the first message with `400 INVALID_ARGUMENT: Thinking level MINIMAL is not supported for this model`, in both the desktop app and the web app. The provider account had credit, and Kimi and OpenAI answered on the same harness, so the failure was not quota or credentials.

The request carried no reasoning effort: the user left the picker on its default. `dsh-llm-pi-ai` omits the `reasoning` option in that case, and pi-ai's Google adapter treats "no reasoning" as "disable thinking". Gemini 3 Flash cannot fully disable thinking, so pi-ai asks for its lowest level — hardcoded as `MINIMAL` for the Flash family. Gemini 3.7 and 3.8 Flash retired `MINIMAL` and reject it outright, so every default-effort request failed before the model ran. The installed pi-ai catalog still advertises `minimal` for those models because its entry only maps `off` to null.

Direct checks against the provider confirmed the boundary: `MINIMAL` returns 400 for `gemini-3.7-flash` and `gemini-3.8-flash`, `LOW` returns 200 for `gemini-3.8-flash`, and `gemini-3.5-flash`, `gemini-3.6-flash`, `gemini-3-flash-preview`, and `gemini-3.1-flash-lite` still accept `MINIMAL`.

## Decision

**The adapter names the lowest accepted level for a Google model that cannot turn thinking off.** `googleThinkingFallback` applies to the `google-generative-ai` and `google-vertex` protocols only. When the resolved model supports no `off` level and neither the call nor the profile names an effort, the adapter sends the first level `getSupportedThinkingLevels` reports instead of leaving the option absent. Models that support `off` keep pi-ai's disabled dispatch, and non-Google protocols are untouched.

**The product declares what Gemini 3.7 and 3.8 Flash accept.** `faberloom-app` overrides `gemini-3.7-flash` and `gemini-3.8-flash` with `reasoningEfforts: { low, medium, high }`. Undeclared levels are pinned unsupported, so `Minimal` disappears from the picker, a default request resolves through the adapter fallback to `low`, and an explicitly stored `minimal` is refused before network I/O with `UNSUPPORTED_REASONING_EFFORT`.

## Alternatives considered

**Force `reasoning: low` on the whole Google route.** Rejected: it would change the default for Gemini Pro and every other model on the route, including models where pi-ai's own disabled dispatch is correct.

**Patch the installed pi-ai catalog.** Rejected: `node_modules` is not ours, the entry is regenerated by the dependency, and the correct level is a deployment/model decision the profile already expresses.

**Catch the 400 and retry at a higher level.** Rejected: it hides a configuration fact behind a second request, doubles latency on every new model, and cannot know which level the provider actually accepts.

**Tell users to pick Low manually.** Rejected: the default selection is the failing path, so a fresh session fails before the user learns the rule. It also leaves the picker offering a level the provider rejects.

## Consequences

A default-effort request to Gemini 3.7 or 3.8 Flash sends `LOW` and succeeds. The picker offers Low, Medium, and High for those two models; Gemini 3.0 through 3.6 keep `Minimal`, which the provider still accepts. A vendor retiring another level later needs the same catalog or override correction; the adapter cannot discover it from a 400 message.

## Testing

`packages/llm/llm-pi-ai/tests/adapter.spec.ts` covers the fallback for both Google protocols, its absence when `off` is supported or the protocol is not Google, and the levels a `modelOverrides` entry exposes. Live checks against `generativelanguage.googleapis.com` pinned the provider matrix above.
