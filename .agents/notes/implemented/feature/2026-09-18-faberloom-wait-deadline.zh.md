# Agent Note: 例程的等待带有截止期限

Status: implemented

[English](2026-09-18-faberloom-wait-deadline.md) | 中文

## 问题

停在 `waitFor` 上的步骤可以永远等待。如果回复始终不来 —— 客户没有回应、后续邮件来自没人轮询的邮箱、人忘了 —— 执行会一直停在 `waiting`，没有信号、没有复核，面板上也无法把「仍在等待答复」与「这个案件已经死了」区分开。计划要求持久调度器核对超时，而执行记录里没有任何可供比较的时刻。

## 决定

停下的执行会记录等待何时不再合理，调度器据此行事。

`packages/faberloom/routines` 增加了一个经校验的 `Config.waitTimeoutMs`（默认一天，低于一分钟会被拒绝）以及一个引擎操作 `expireWaits(now)`。当 `runSteps` 让某个步骤停在 `waitFor` 上时，记录得到 `deadlineAt = now + waitTimeoutMs`；应答会清除它，完成、失败与重新校验也会。`expireWaits` 会把每个 `deadlineAt` 已过、仍处于 `waiting` 的执行移到 `needs_review`，把该等待步骤标记为 `WAIT_TIMEOUT` 失败，并清除该字段 —— 因此之后的一趟不会把同一案件过期两次。

`packages/faberloom/execution` 把它作为一趟的第四步调用（在 tick 与 reconcile 之后），并在新的 `DispatchReport.expired` 中报告这些 id。

持久化改动是执行记录上的一个可选字段 `deadlineAt: string | null`，以 `.default(null)` 声明。该字段出现之前写入的行读回为 null，因此表保持 schema 版本 1，持久化各道门也继续通过；产品域不是已发布的会话格式，因此不需要持久化变更确认。面板通过 `executionRow` 读取它，并在等待旁显示该时刻。

## 考虑过的替代方案

- **按步骤声明超时。** 表达力更强，也是正确的终态：它需要在例程步骤 schema（例程记录与其各版本）上加字段、加编辑器控件，并有其迁移过程。部署级默认值就足以回应本切片要解决的问题。
- **在 `tick` 内过期。** 否决：`tick` 接收事件并以它恢复了什么作答；超时不是事件，把两种原因塞进一个操作会让面板与工具无法区分。
- **把执行标记为 `failed`。** 否决：没有人应答，并不等于例程在其工作上失败了。复核才是由人决定的地方，也是大多数步骤的失败策略已经表达的意思。
- **重试等待或重发通知。** 目前否决：重试需要本产品尚不具备的通知渠道，而一个永不升级的截止期限正是本切片要修掉的缺陷。

## 后果

- 回复始终不来的案件会自行到达 `needs_review`，原因 `WAIT_TIMEOUT`，等待步骤失败，因此面板显示的是需要人的案件，而不是看起来很有耐心的案件。
- 截止期限是部署策略，而不是按例程设置：为了更早发现丢失的回复而缩短它，也会让合法的长等待过期。按步骤覆盖是推迟的工作。
- 过期不会重新通知任何人；它把案件呈现在 owner 本就会看的地方。
- `DispatchReport.expired` 让过期对驱动这些趟的人可见，包括自行调用 `runOnce` 的部署。
