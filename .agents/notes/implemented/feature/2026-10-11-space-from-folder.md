# Agent Note: Adopt an existing folder as a Space

Status: implemented

English | [中文](2026-10-11-space-from-folder.zh.md)

## Problem

A FaberLoom Space always mirrored the deterministic `<DSH_HOME>/spaces/<ref>` area: `faberloom-view`'s `ensureSpaceWorkspace` created that directory and registered it as a Workspace on first use. A user who already keeps a client's files in a folder — the common case, and the point of the product — could not point a Space at it, so the agent's file tools and the sidebar conversation area never worked on the folder the user actually uses. `faberloom-spaces` already carried `workspaceId` on the record ("the harness workspace this space mirrors when a Workspace is adopted as a Space") and `UpdateSpaceInput` already accepted it; only the adoption action was missing.

## Decision

The Spaces panel adopts an existing folder as a Space's conversation area.

- `faberloom-view` gains the Remote `adoptSpaceWorkspace(id, path)`. It resolves the folder through the mounted workspace registry — reusing a Workspace already registered at that path, otherwise creating one titled after the space — and writes the resulting `workspaceId` onto the space through `ctx.faberloomSpaces.update`. It throws when the workspace registry is not mounted, matching `openSpaceWorkspace`.
- `ui-faberloom` injects `remote.directoryPicker` (the native picker in the Desktop, the browse picker on the Web) and adds the **"Usar una carpeta existente…"** action beside *Nueva conversación en este espacio* in the space detail. The flow lives in `src/client/adopt-space-workspace.ts` (`runAdoptSpaceWorkspace`) so it is testable against a stub context: pick, then adopt, then reload the overview; a cancelled pick, a failed pick, or a refused adoption leaves the current Workspace untouched.
- `faberloom-view`'s `./remote` is generated by the Typert build, so the new method reaches `ctx.remote.faberloomView` on the next `build:lib:host`.

## Alternatives considered

**Create the Space and the Workspace in one new Remote (`createSpaceFromFolder`).** Rejected: adopting a folder is a property of an existing Space, and a Space may be created first (with an agent, a parent, and inheritance) and pointed at a folder later.

**Copy the folder into `$DSH_HOME/spaces/<ref>`.** Rejected: the user's point is to work on their own folder, not a copy; copying also forks the files the agent and the user both edit.

**Write the path straight into the space record instead of registering a Workspace.** Rejected: the sidebar, the session `cwd`, and the file tools all resolve through the workspace registry; a raw path would work in one place only.

**Let the picker run in the host.** Rejected: the Desktop's picker is a native dialog owned by the Electron shell and the Web's is a browser surface; both already expose the `remote.directoryPicker` namespace the client half must call.

## Consequences

A Space can now name any folder the user can pick, and the sidebar Workspace, the session working directory, and the Space all resolve to it. A folder already registered as a Workspace is reused, so adopting it twice never forks a second entry. The deterministic `<DSH_HOME>/spaces/<ref>` area stays the default for a Space that never adopted one. Read-only identities keep the action gated by the same panel rules as the other Space writes.

## Testing

`packages/faberloom/view/tests/adopt-space-workspace.spec.ts` covers registering the picked folder and writing `workspaceId`, reusing a Workspace already at that path, and failing loud without the registry. `packages/client/ui-faberloom/tests/adopt-space-workspace.client.spec.ts` covers the pick-then-adopt flow, a cancelled pick, a failed picker, and a refused adoption. The `ui-faberloom` panel suite provides the injected `remote.directoryPicker` in its harness.
