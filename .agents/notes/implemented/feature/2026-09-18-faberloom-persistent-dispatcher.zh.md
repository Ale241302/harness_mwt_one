# Agent Note: FaberLoom 的例程在无人、无打开会话时也能推进

Status: implemented

[English](2026-09-18-faberloom-persistent-dispatcher.md) | 中文

## 问题

计划承诺：关闭浏览器或对话不会让工作停下 —— 带 `date`、`recurrence`、`email` 或 `event` 触发器的例程必须自行启动，处于等待的运行必须在无人打开面板的情况下被推进与核对。引擎所需的一切都已存在 —— 持久执行、幂等键、等待、效果账本、调度锁，以及 ingest 路径 —— 但没有任何东西调用它们。`tick` 与 `reconcile` 只能从面板按钮或模型工具触达，因此没有人碰过的例程永远不会运行，而 `faberloom-execution` 仍只是骨架。

## 决定

`packages/faberloom/execution` 成为计划所映射的调度器。`ctx.faberloomExecutions` 接收部署身份（`ownerId`）与节奏（`enabled`、`intervalMs`，默认关闭与一分钟），立即跑一趟，之后按定时器重复，并随自己的 fiber 停止。`runOnce(now)` 是公开的，因此部署可以用自己的时钟驱动。

在例程引擎自带的调度锁之下，一趟执行：

1. 启动每个 `date` 触发器时刻已过的已激活例程，以及每个 `recurrence` 触发器进入新时间槽的已激活例程；
2. 通过 `tick` 推进有可运行步骤的执行；
3. 通过 `reconcile` 把处于复核、效果仍未决的执行移到 `RECONCILE_REQUIRED`。

幂等这件事被留在它该在的地方 —— 引擎的去重，而不是定时器。`date` 启动以触发器指定的时刻为键，`recurrence` 启动以其落入的间隔槽（`floor(now / interval)`）为键，因此重复的一趟、重启后的一趟，以及服务同一 owner 的两个进程，各自都只产生一次运行。这也是不存游标的原因：键可以从例程与时钟推导出来。

`recurrence` 的 match 接受 `every:<分钟>`、`<n>m`、`<n>h`、`<n>d`；其他文本会在每个进程中报告一次并指出是哪个例程，然后跳过。失败的一趟只记录警告并保持定时器存活。

## 考虑过的替代方案

- **每个例程存一个游标。** 否决：推导出的键不需要迁移，不会与它所描述的执行漂移，并且已经跨进程去重。
- **复用 `ctx.schedule` 或 `ctx.jobs`。** 否决：两者都是会话或进程局部的，而计划恰恰说这种情况不能成立。
- **把 tick 放进例程引擎本身。** 否决：引擎是存储之上的库；其中的定时器会在每个为测试而挂载它的组合中触发，并会掩盖谁有权启动工作。
- **在加载时调用 `startExecution` 并信任内存标记。** 否决：重启的进程，或同一 owner 的第二个进程，会再次启动该运行。
- **遇到无法解析的间隔就让插件失败。** 否决：一个坏例程会把整个调度器拖垮，并静默停掉其他所有例程；在日志中指明它就足够响亮。

## 后果

- 带 `date` 或 `recurrence` 触发器的例程现在可以在浏览器关闭时运行，其步骤在 handlers 包已经拥有的按执行隐藏会话中执行。
- `email` 或 `event` 触发器仍在等待有人调用引擎的 ingest：一趟无法凭空造出事件。入站接收器（webhook 或邮箱轮询）仍是独立的切片，永远等待的步骤的截止期限策略亦然。
- 该行只携带一个 owner，与每用户一个进程相符；单个调度器服务多个 owner 需要另一种身份绑定。
- 核对现在无需人盯着也会发生。效果仍未决的运行会自行到达 `needs_review`，并出现在面板读取的执行中。
