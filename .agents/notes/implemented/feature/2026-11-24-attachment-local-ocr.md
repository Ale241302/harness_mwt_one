# Agent Note: attachments without a text layer are read by local OCR

Status: implemented

English | [中文](2026-11-24-attachment-local-ocr.zh.md)

## Problem

Attachment ingestion converted documents with `anydoc` and nothing else, so two real email cases stayed unread. A PDF whose pages are pictures made the converter exit 3 (`needsOcr`); with `ocr: 'reject'` the attachment was dropped as "sin texto extraíble", and the `hosted` path needed `FIRECRAWL_API_KEY`, which the deployment did not have. An image never even reached conversion: `formatForAttachment` knew no image extension, so a photo of a purchase list was reported `unsupported`. The mail reader deliberately keeps inline images (`imap.ts`) for a consumer that did not exist, and `deepseek-flash` cannot see images, so there was no vision path either. A third case appeared as soon as the OCR path shipped: a Word, Excel, or PowerPoint file whose pages are scanned images. `anydoc` opens the package, finds no text, and the attachment became `empty` with nothing naming the missing renderer.

## Decision

Read attachments without a text layer with **local OCR**, through the subprocess seam, best-effort, and keep `hosted` as an option for a deployment that buys a key.

- `packages/faberloom/inbound/src/ocr.ts` owns both paths, and every page goes through the same three steps. `straighten` runs `deploy/ocr/ocr-tools.py deskew` through the subprocess seam: the helper searches the rotation between -12 and 12 degrees that concentrates the ink on the fewest rows, and returns the page untouched when the angle is under 0.5 degrees or when Python is missing. `recognize` then runs `tesseract <page> stdout -l spa+eng --psm 3 tsv`, rebuilds the lines from the word rows, and keeps their median confidence; that rebuild produced byte-identical text to the plain-text renderer on both real documents measured. When the median falls under 75 the page is re-read with RapidOCR (`ocr-tools.py rapid`), which loads its ONNX models per process, so `readPages` collects every weak page of a document into one call. `ocrPdf` renders the PDF with `pdftoppm -r 200 -png` into a scratch directory and marks pages with `--- página N ---`. Both spawn through `SubprocessRuntime.spawn` (no shell, no `node:child_process`), resolve their binaries with `resolveExecutable`, and never throw past the caller.
- Bounds are explicit and each one has a reason: 25 MB per attachment (the existing `MAX_INPUT_BYTES`), 10 pages per PDF, 20 s for one Tesseract run, 20 s for straightening one page, 90 s for one RapidOCR batch, 180 s per PDF, 200 KB of retained text. A failure, a timeout, or a protected PDF returns the text collected so far or the reason it stopped, exactly like the converter does today.
- `deploy/ocr/ocr-tools.py rapid` owns what the second engine returns: it groups detected lines into visual rows (centres within 60 % of the shorter line's height), joins a row's cells with ` | ` when at least two rows carry more than one cell, and prefixes `[?]` to any line it scores under 0.85 that carries four or more characters. It reads a printed page with a Latin recognition model — the default model drops word spaces and accents, turning `Muito Work Limited` into `MuitoWorkLimitada` — and keeps the default model for a page whose median line confidence is under 0.98, where it read twice as many fields on the hand-written photo. `models/latin_rec.onnx` (9 MB) is downloaded at build time from the RapidOCR model zoo with a pinned SHA-256; `models/latin_dict.txt` is committed. Without the model every page falls back to the default one.
- `packages/faberloom/inbound/src/documents.ts` classifies an attachment before converting it: `IMAGES` maps raster extensions to a media type, and the declared `mediaType` decides when the name carries no usable extension (an inline picture pasted into a message). An image goes to `ocrImage` or is reported `ocr-disabled`; it never reaches `anydoc`, which has no image path and would only produce a fake failure. A document goes to `anydoc` first; its text wins when it exists, and a PDF that yields none falls back to `ocrPdf`.
- `packages/faberloom/inbound/src/office.ts` covers the scanned office file. `ocrOffice` writes the bytes under the attachment's own extension, runs `libreoffice --headless --norestore --convert-to pdf --outdir <scratch>` with a private `-env:UserInstallation` profile (the shared profile is one lock, so two attachments in one pass would otherwise collide), reads the produced PDF under a 50 MB cap, and passes it to `ocrPdf`. `documents.ts` falls back to it for `doc`, `docx`, `xls`, `xlsx`, `ppt`, `pptx`, `odt`, `ods`, `odp`, and `rtf` when `anydoc` yields no text under `local`; `xls` joins `FORMATS` with its own alias. Bounds: 60 s for the conversion, 150 s for the whole attempt, 50 MB per produced PDF, and the scratch directory is removed on success and on failure. A missing LibreOffice reports `converter-missing`; a non-zero exit, no PDF, or an empty PDF reports `failed`, which `documents.ts` surfaces as `ocr-failed`.
- `AttachmentSkipReason` gains `ocr-disabled` and `ocr-failed`, so a reader can tell "this deployment has no OCR" from "OCR ran and read nothing". `tool-faberloom` renders both as model-facing notes.
- Configuration: `FABERLOOM_OCR` (`off` | `local` | `hosted`) is the switch, as the `ocr` field of `tool-faberloom` and `faberloom-view`, defaulting to `off` in code. The gateway writes that field on both rows from `FABERLOOM_OCR` — default `local`, and an unknown value aborts the boot with the same FATAL line an invalid tools mode uses — while `ANYDOC_OCR` still governs the converter's own hosted path. `resolveOcrMode` also accepts `local` in `anydocOcr`, so a profile written before the field existed keeps working; an explicit `ocr` wins.
- `Dockerfile` installs the OCR packages (`tesseract-ocr`, `tesseract-ocr-spa`, `tesseract-ocr-eng`, `poppler-utils`: 69 packages, 38.4 MB of downloads, 115 MB of disk) and, for office documents, `libreoffice-writer`, `libreoffice-calc`, `libreoffice-impress`, and `fonts-liberation` in the same `apt-get`: 171 packages, 154 MB of downloads, 506 MB of additional disk, which takes the image from 329 MB to 991 MB. `fonts-liberation` keeps Arial metrics, so a document written in Arial does not reflow into DejaVu before OCR reads its columns. A second `RUN` installs `python3-pip` and, into `/opt/ocr/py`, `rapidocr-onnxruntime` with `onnxruntime`, `opencv-python-headless`, `numpy`, `Pillow`, `shapely`, `pyclipper`, `six`, and `PyYAML`: 350 MB of disk, measured. `opencv-python-headless` rather than `opencv-python` is 137 MB instead of 203 MB with identical readings. `COPY deploy/ocr/ /opt/ocr/` ships the helper. No capability is added to the container.

## Alternatives considered

**Hosted OCR only.** `anydoc --ocr hosted` already existed, but there is no Firecrawl key in the deployment, every page would cost money, and a purchase order would leave the infrastructure. The owner's decision is the opposite: documents stay here.

**A vision model.** `deepseek-flash` cannot see images and no provider key is deployed; a vision provider would be a second external dependency and a data-class problem for business documents.

**OCR the rendered page instead of the PDF text layer.** `pdftotext` would be cheaper than rendering plus recognition, but a mixed PDF would still need page-level decisions, and `anydoc` already produces the better Markdown (headings, tables) whenever a text layer exists.

**Keep images `unsupported`.** The reader keeps inline images on purpose and the product asks for "la foto de una lista"; reporting a supported case as an unsupported format hides a capability the deployment now has.

**Convert office documents in a sidecar container.** LibreOffice adds 459 MB to the filesystem and 662 MB to the reported image size, and every tenant's supervisor shares one image. A separate converter container would keep the app image where it is, at the cost of a second service, its own lifecycle, and a transport between the two. This change takes the in-image path because it is the smallest one that keeps the document on the deployment; a deployment with a hard image budget should take the sidecar (measured alternatives: the `-nogui` module variants add 431 MB, and `libreoffice-writer-nogui` alone adds 368 MB).

## Consequences

- The conversion path is now three converters with one classification in front: `anydoc` for documents, Tesseract for pictures and scanned pages, and LibreOffice plus Tesseract for a scanned office file. A bad render cannot break the mail read; it degrades to `timeout`, `ocr-failed`, or `empty` with the reason on the tool result.
- Straightening costs 0.2 to 0.6 s per page and is skipped entirely when `python3` is absent; the second engine costs about 14 s for the pages that need it. A ten-page document that escalates on every page no longer fits the 90 s a Tesseract-only pass had, so the document bound is 180 s. Both extra steps share that budget: a page that reaches its deadline keeps the first reading instead of failing the attachment.
- The second engine is the only part that needs the ONNX models, and it is optional at runtime: a deployment without `/opt/ocr/py` reads every page with Tesseract and reports the same text the earlier path produced.
- The image is larger by ~115 MB for OCR and ~460 MB more for LibreOffice, and the build needs `apt-get` reachability. A deployment that cannot install Tesseract or LibreOffice reports `converter-missing` and keeps working.
- Local OCR reads PDFs, raster images, and office documents. An office file is rendered first, so its pages arrive as the renderer drew them: Tesseract returns text, not layout, and a table arrives as lines.
- An image has no hosted path. `local` reads it with Tesseract, and any other mode reports `ocr-disabled`. `hosted` still covers a scanned PDF through anydoc, which needs a Firecrawl key this deployment does not carry, so no picture leaves the machine.

## Testing

`packages/faberloom/inbound/tests/ocr.spec.ts` covers the resolved binaries (both, none, image-only, and the Python that runs the helper), `readTesseract` rebuilding lines and paragraphs with its median confidence and ignoring level rows, one image read from the written file with its argv, empty bytes, a missing binary, a non-zero exit, a spawn failure, a page timeout, a page Tesseract did not trust re-read by the second engine, a weak page kept as it is when the second engine is absent, a straightened page read from its copy, a page read as it arrived when straightening fails, page rendering and per-page marks, the page cap and its unread notice, a protected PDF, a document whose pages all failed, a missing renderer, text truncation, and one shared second reading for only the weak pages. `documents.spec.ts` covers the classification (`imageMediaType`, `resolveOcrMode`), an image read by local OCR, an image with OCR off or hosted, a missing Tesseract, an empty OCR result, a failed OCR process, an image typed by media type, a `needsOcr` PDF that falls back, a clean-but-empty PDF that falls back, a PDF the converter reads (OCR never starts), a format outside the office list that is not OCR'd, an office file that falls back to LibreOffice with its converter reason kept when local OCR is off, a missing LibreOffice, a failed conversion, a legacy `.xls`, an OCR page timeout, an attachment with no bytes, and the previous converter paths. `office.spec.ts` covers both resolutions of `resolveOfficeBin`, the written extension, the converter argv, per-page marks, the scratch directory removed on success and on failure, a missing converter, missing OCR binaries, empty bytes, a PDF named differently by the converter, a conversion that writes no PDF, a zero-byte PDF, a PDF past the size bound, a conversion timeout, a whole-attempt timeout reached during OCR, and a name whose extension is unusable.

Real evidence in a container built from the shipped apt line (`node:22.23.2-bookworm-slim` + the three LibreOffice modules + `fonts-liberation` + Tesseract and poppler): a `.docx` was built whose only content is a 1241×1754 scan of "PEDIDO 20845 / SKU 515007019 / 10 337,70 / Total USD 3.377,00" (LibreOffice extracts 1 byte of text from it), and `ocrOffice` on that file returned `--- página 1 ---` with the SKU, quantity, and total in 1.85 s through the real `libreoffice`, `pdftoppm`, and `tesseract`. A reading of `515007015` was recorded from that fixture at first; it was the fixture, rasterized twice, not the document. On the real purchase order Tesseract reads both part numbers and the total correctly at 150, 200, 300, and 400 dpi.

Real evidence on the four documents that drove the second engine, taken from the owner's mailbox (one 12 MP phone photo of a hand-written invoice and three thermal receipts, each also rotated 7 degrees either way, twelve variants in all): Tesseract alone scored 3 of 5 checked fields on the photo and 0 to 2 of 5 on the rotated receipts; after `deskew` the receipts returned to 5 of 5 and kept their word spacing; RapidOCR scored 5 of 5 on all twelve. The photo's median word confidence was 52 where printed pages score 90 to 96, which is where the 75 floor comes from. Costs measured in the deployed container: straightening 0.2 to 0.6 s per page (8.4 s when it wrote a full-resolution PNG, which is why the helper writes JPEG at quality 95), Tesseract 1.8 to 4.7 s, RapidOCR 9 to 17 s per image plus one model load per batch.

Measured on the same four documents for the model choice and the rendering. The default model read `MuitoWorkLimitada`, `EnsaladaCaprese`, and `Coca cola zero` as one word each; the Latin model read `Muito Work Limitada`, `Ensalada Caprese`, `Coca cola zero`, `Adriana Jiménez Leiva`, and `resolución` with its accent, in 8 s against 14 s for the same receipt. On the hand-written photo the Latin model recovered 2 of 6 checked fields where the default model recovered 4, and its median line confidence was 0.966 against 0.990 to 0.996 on the three receipts, which is where the 0.98 boundary comes from. After the rendering, the receipt carries `Sirloin 450 gr | 11.382`, `Subtotal | 23.780`, and `3Articulos | TOTAL | 29.249` as rows, and the invoice carries `CANT | DESCRIPCION | MONTO`.

The hand-written identification number is the one field that no engine measured reads: Tesseract on the full page returns noise, on a cropped and upscaled line it returns `3-102-761210`, `3-102-751316`, or `3-102-75416` depending on the page-segmentation mode; RapidOCR returns `3-102-7s1716` on the page and `3-102-75110` on the line crop; the Latin model returns `3-102-7s716`. A local vision model was measured and rejected: Qwen2.5-VL-3B at q4 on this CPU returned `3-102-3535` for the cropped line and `04-03-19` for the full page, in 60 to 90 s, so the 3 GB it would add buys nothing. That is why the line is marked `[?]` instead: the number of checked fields that do read correctly (amount, invoice number, cédula of the issuer) is four, and the wrong one is the field that drives a payment to a supplier, which must not pass as a value.

Real evidence on the deployed container: the OC 20845 PDF has a text layer (`pdftotext` returns 1463 bytes) and `anydoc` converts it (exit 0, 1592 bytes of Markdown), so the tool path returns the converter's text and OCR is not invoked for it; `ocrPdf` on the same file as the tenant uid returns the order lines (SKUs, quantities, prices) in ~4 s, and `image005.jpg` (a photo of a business card) returns its name, phone, and e-mail.
