# Agent Note: FaberLoom 备份捕获各持久域

Status: implemented

[English](2026-09-20-faberloom-backup.md) | 中文

## 问题

`ctx.faberloomBackup` 曾是已注册但没有任何行为的服务：计划的备份切片（E8）要求对产品知识进行导出、恢复与完整性校验，而该包的 README 也承认它不承载任何持久记录。没有它，产品无法对空间、智能体、例程、执行、教导、授权、连接或 MCP 令牌做快照 —— 只有基础设施的卷备份存在，而且恢复过程无法证明它读到的载荷就是它写入的载荷。

## 决定

该服务拥有一个持久域，并通过存储域设施对其他产品域做快照。

`packages/faberloom/backup` 声明 `faberloom_backup`（一张 `backups` 表）以及九个产品域及其表的固定清单。`createBackup(ownerId, options?)` 通过 `ctx.storageDomain.get(name)` 读取每个已打开的域，复制每张表的记录，并写入一行，其中包含规范 JSON 载荷、每张表记录数与 sha256 摘要组成的清单、载荷摘要以及可选备注。`verifyBackup` 从存储的载荷重新计算每个摘要，`restoreBackup` 在写入任何内容之前拒绝摘要已不匹配的载荷；恢复通过 `table.put` 对每条记录做 upsert，并把本进程未打开的域报告出来而不是失败。`listBackups`、`getBackup` 与 `deleteBackup` 补全接口。

各域通过设施的诊断性 `get` 接口读取，而不是按服务逐个添加导出方法，因此一个模块即可覆盖全部九个域，无需在每处定义一份定制契约；表名就是 `spec.ts` 中的固定清单。静态加密与异地保留仍由平台备份（gpg、rclone）负责。

## 考虑过的替代方案

- **按服务各自的 export/import 方法。** 每个服务拥有其域，可以返回类型化快照。本切片否决：要维护九份契约，而学习服务现有的 `exportKnowledge` 已经展示了这种重复；通用读取可以避免它。
- **为快照新建一个存储后端。** 否决：域形式已经提供持久化与 schema 校验，而快照本身就是普通记录数据。
- **在服务内加密载荷。** 否决：部署已经加密卷副本，在产品内再造一套密钥管理面只会增加成本而没有消费者；README 记录了这条边界。

## 后果

- 快照得到端到端的完整性校验，被篡改的载荷会在任何写入之前被拒绝，因此恢复不可能悄悄带回已损坏的知识。
- 服务捕获处于打开状态的域；插件未挂载的域会从清单中省略，这在 `listBackups` 中可见，而不是静默地显示为空。
- 恢复执行 upsert；它不会对已对外部系统产生的效果做核对，后续切片才会接上 Conexiones 界面与周期运行。
