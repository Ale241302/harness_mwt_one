# Agent Note：Correo 用自己的预算读取 MCP 正文，并在图片到达时逐张绘制

Status: implemented

[English](2026-11-23-correo-reads-without-waiting.md) | 中文

## 问题

通过 Hostinger MCP 端点读取邮件正文时会间歇失败，报 `"messages_text" … did not complete within 5000ms`。面板把所有 MCP 调用都限制在列表预算内，于是一封服务器需要五秒以上渲染的大型简报会直接显示为错误。远程图片还有第二重可见代价：面板要等整封邮件的所有抓取都结束后才统一绘制，因此有十几张图片的邮件在等待最后一张时一直空白。

## 决定

### 正文有自己的预算

`MCP_BODY_CALL_TIMEOUT_MS` 为 20 秒，只用于 `messages_text`。`account_current`、`folders_list` 与 `messages_list` 保持五秒的面板预算，这样不可达的服务器仍能快速让其余界面显示出来。正文读取是 owner 主动等待的一次操作，服务器可能需要数秒来渲染。

### 正文只读一次并复用

`emailRead` 按 owner 与合成消息 id 保存最近 50 封 MCP 正文，保留十分钟。重新打开同一封邮件时直接从该映射返回，不再调用服务器；读取时丢弃过期条目，超过上限时丢弃最旧的，失败的读取绝不保存。该映射属于视图服务，随服务一起释放。

### 每张图片到达即绘制

面板仍然按地址调用一次 `emailImage`，并在本次会话中缓存字节，但不再等待 `Promise.all`，而是每解析出一个地址就以一次独立的状态更新发布。框架的清理器和 `img-src data:` 策略不变。

## 备选方案

**提高所有 MCP 调用的面板预算。** 否决：挂起的服务器会让邮箱列表等二十秒才显示 IMAP 已有的内容。

**超时后重试正文读取。** 本切片否决：最坏等待翻倍，还掩盖了原因；专用预算加缓存已覆盖报告的场景。

**把正文放进持久缓存。** 否决：正文是渲染快照，不是产品数据；owner 保留的内容已由会话拥有。

## 后果

能在二十秒内返回的正文不再出现间歇错误，重新打开邮件十分钟内不产生服务器调用。内存按每个服务实例 50 封正文为上限。图片逐张出现，简报在其余图片到达时已经可读。超过二十秒的正文仍会明确失败。

## 测试

`corepack pnpm run typecheck` 通过；`vitest run packages/faberloom/view/tests`（321 项）与 `packages/client/ui-faberloom/tests`（287 项）通过。新增覆盖：同一正文读两次只调用一次 `messages_text`；列表保持五秒预算而正文使用二十秒预算；失败的读取会重试；过期条目会重新读取。
