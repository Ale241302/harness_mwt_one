# Agent Note: FaberLoom 为每个 owner 播种计划派生的代理名册与例程

Status: implemented

[English](2026-09-18-faberloom-defaults.md) | 中文

## 问题

新的 FaberLoom owner 面对四个空面板：没有任何东西告诉他该创建哪个代理、该挂哪些技能，或者例程长什么样。产品计划与界面示意图其实已经用一个走通的例子回答了这些问题 —— 三名代理的名册与 `Pedido → proforma` 例程 —— 但没有任何机制把这个例子带进新工作区，而计划本身也明确警告不要按每个任务自动填充目录。

## 决定

由 `packages/faberloom/defaults` 拥有初始内容。它在存在 `ctx.faberloomAgents` 与 `ctx.faberloomRoutines` 的位置挂载，接收部署身份（`ownerId`、`role`、`readOnly`、`skillsCatalogRoot`），并在激活时播种一次。

目录就是 `src/catalog.ts`，取自计划：代理界面中的名册（`Recepción`、`Revisión de pedidos`、`Proformas`），以及例程界面中的 `Pedido a proforma` —— 它的四个步骤分别走三个已随附的处理器：一次 `agent` 轮次、一次 `mcp` 操作，以及等待复核以结案的一次 `wait`。播种出的例程保持 `draft`，因此由邮件驱动的触发器在 owner 激活之前不会运行。

三条规则让这一趟既可安全重复，也可安全跳过：

- **由角色决定技能。** 只有 owner 在 `<DSH_HOME>/skills` 下的自己上传、或 `skillsCatalogRoot/<role>` 下的角色目录确实随附了该技能时，代理才会获得它；部署的技能目录始终是唯一来源，因此不会有任何复制。
- **先按名称匹配再创建。** 名称已存在的条目会被跳过，这使得部分完成后的重试在没有事务的情况下也是幂等的。
- **每个 home 一个标记。** `<DSH_HOME>/faberloom-defaults.json` 只会由确实创建了内容的那一趟写入，因此之后的启动既不会重复，也不会复生 owner 已删除的条目。

这一趟通过产品服务完成，而不是直接写存储行，因此播种出的代理与例程携带与面板中创建者相同的校验、版本与身份。

## 考虑过的替代方案

- **在首次读取面板时播种。** 否决：会写入的读取会让调用方意外，而且两个打开的面板会竞争。
- **只要名称缺失就播种。** 否决：它会复生 owner 有意删除的内容。
- **把目录作为部署文件随附。** 目前否决：计划中的例子属于产品内容，而文件需要模式、校验与第二条评审路径；该推迟记录在包的 README 中。
- **把角色的技能复制进 owner 自己的技能文件夹。** 否决：配置已经把角色目录暴露为原生技能，复制会让面板中的每个技能翻倍。
- **自动激活播种出的例程。** 否决：在没有 owner 决定的情况下让触发器开始投递由邮件驱动的工作，与安全默认背道而驰。

## 后果

- 新的 owner 会看到一条 `draft` 例程与三名代理，且每名代理已带上其角色随附的技能。
- 改变新 owner 收到什么需要修改 `src/catalog.ts`；目前还没有由部署提供的目录。
- 标记以 owner home 为键，因此共享同一个 home 的两个部署会共享同一个标记。
- 计划中的名册是起点，不是业务策略：每个播种出的值都能在面板中编辑，计划中「不要自动填充目录」的规则对代理之后所做的一切仍然成立。
