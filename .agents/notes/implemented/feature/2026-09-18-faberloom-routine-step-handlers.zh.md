# Agent Note: 每个 FaberLoom 例程执行都在一个隐藏会话中运行步骤

Status: implemented

[English](2026-09-18-faberloom-routine-step-handlers.md) | 中文

## 问题

例程引擎拒绝激活任何例程：当某个步骤引用了没有任何插件注册的处理器时，`activateRoutine` 会报告 `MISSING_HANDLER:<step>:<handler>`，而产品层当时没有注册任何处理器。因此面板中显示的每个例程都是静止的 —— 执行面板可以读取、启动与推进，但没有任何东西能真正运行。引擎在智能体循环内执行工具，因此 `agent` 或 `mcp` 步骤需要一个存活的 Agent 与会话；而步骤处理器从例程引擎中运行，既无环境智能体，也无会话与归属者。

## 决定

由 `packages/faberloom/handlers` 拥有这些步骤处理器。它通过 `ctx.faberloomRoutines` 注册三个名称，并各自随自己的 fiber 一起移除：`wait`、`agent` 与 `mcp`。

`agent` 与 `mcp` 在**每次执行一个隐藏的持久会话**中运行各自的轮次：在第一个此类步骤时创建，并由同一次执行的后续步骤复用，因此多步骤例程会累积为同一段对话。该会话通过 `fs` 服务解析部署的工作目录 —— 组装后的系统提示词会读取 `{{cwd}}`，因此缺少它的会话在第一个轮次就会失败 —— 并标记为 `origin: "subagent"`，这正是工作区树用来把 owner 会话列表过滤掉的分类。步骤轮次使用部署的默认模型选择与配置的全局工具面。

处理器从会话的持久日志中选出最后一条非空的 `assistant/message` 文本、`turn/end` 类型，以及 `tool/call` 的名称与调用 id，并把它们与会话 id 一起存为步骤结果。该 id 就是审计链接：执行记录指明会话，会话日志保存轮次。

只有以 `completed` 结束的轮次才会结束其步骤。任何其他结束方式 —— `error`、`aborted`、`blocked`、`max-tokens`，或根本没有 `turn/end` —— 都会抛出异常，并在消息中给出会话 id 与失败原因，因此例程的 `failurePolicy` 决定后续处理，执行面板也会显示原因。

## 考虑过的替代方案

- **在 owner 自己的对话会话中运行步骤。** 否决：由邮件或计划触发的例程没有在场用户，且把例程轮次混入某个人的对话会隐藏该运行自身的记录。
- **按 owner 复用一个会话。** 否决：并发的执行会在同一段历史中交错，后续执行会继承一段无关的对话。
- **不使用 Agent 的模型补全。** 否决：例程步骤的意义在于调用产品的 MCP 工具与技能，而这些只存在于智能体循环中。
- **通过省略 `cwd` 来隐藏会话。** 在生产中失败后否决：部署的系统提示词要求 `{{cwd}}`，轮次在到达模型前就终止了。隐藏方式改为 `origin: "subagent"`，工作区树本就会过滤它。
- **把任何已结束的轮次都视为成功。** 否决：它会把失败的轮次标记为已完成的步骤，正是这一点掩盖了缺少 `cwd` 的缺陷，直到步骤结果开始记录失败原因才暴露。

## 后果

- 步骤引用了未注册处理器的例程仍会激活失败；发布的配置挂载了处理器行，因此开箱可用的名称是 `agent`、`mcp` 与 `wait`。
- 隐藏会话就是普通的持久会话：它们出现在会话存储中，并存活到处理器服务被释放为止，而不是到执行完成时。
- 记录下来的文本以模型实际产出为界；面板显示所选步骤的文本，并在标题中给出完整值，记录则原样保留。
- 按步骤选择模型与权限留待后续；每个步骤轮次都使用部署默认值。
